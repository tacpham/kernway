# KEP-0003: Bean override resolved at compile time

> Backfilled. The decision predates this process; see the note in
> [README](README.md#a-note-on-the-first-four).

## Summary

Every framework default is a bean marked `#[default_impl]`. A user bean for the
same type replaces it silently. Two user beans for the same type are an error,
not a coin flip, unless exactly one carries `#[primary]`.

The wiring that decides this is generated by `#[derive(Component)]` at compile
time. What remains at runtime is a map lookup.

## Motivation

Spring's DI is resolved at runtime by reading annotations off loaded classes. Two
things follow, and both are the motivation here.

**Failures arrive late.** A missing or ambiguous bean is a startup exception —
`NoSuchBeanDefinitionException`, `NoUniqueBeanDefinitionException`. In a large
application that can mean the failure appears in an environment where a
configuration profile differs, rather than on the developer's machine.

**Rust cannot do it anyway.** There is no runtime reflection. Nothing can walk the
loaded types looking for `#[component]`, because at runtime there are no
annotations left to walk. Any DI container in Rust must decide its wiring while
the compiler still has the information.

The second point makes this less a choice than a constraint. The choice is what to
do with the constraint — and the answer is to take the failure modes with it.

Expected outcome: a missing dependency is a build error naming the type; an
ambiguous one is a build error naming the conflict; overriding a framework default
requires no registration step.

## Guide-level explanation

**The framework ships a default:**

```rust
#[component]
#[default_impl]          // "use this only if the user supplied nothing"
struct DefaultErrorHandler;
impl ErrorHandler for DefaultErrorHandler { /* ... */ }
```

**You override it by existing:**

```rust
#[component]
struct MyErrorHandler;
impl ErrorHandler for MyErrorHandler { /* ... */ }
```

There is no `@Primary`, no `@ConditionalOnMissingBean`, no exclusion list. Your
bean is a user bean, the framework's is a default, and a user bean wins.

**Two of yours is a mistake, so it is reported:**

```rust
#[component] struct JwtAuth;    impl AuthExtractor for JwtAuth { }
#[component] struct ApiKeyAuth; impl AuthExtractor for ApiKeyAuth { }
// error: multiple beans implement `AuthExtractor`
// help: add #[primary] to the one that should be used by default
```

Add `#[primary]` to one, or ask for a specific one with a qualifier, or take all
of them with `Vec<Arc<dyn AuthExtractor>>`. What you cannot do is get one of them
arbitrarily and find out in production which.

**Registration order does not matter.** `register_component` only declares;
`refresh` sorts topologically and builds. Register a controller before the service
it needs and it still works.

## Reference-level explanation

**Origin drives the override rule.** Every bean carries a `BeanOrigin`:
`FrameworkDefault` (`#[default_impl]`), `User` (`#[component]`), or `Builder`
(registered directly). When a user bean lands on a type that holds a framework
default, the default is dropped. When a default lands on a type that already holds
a user bean, the default is skipped.

**Resolution order**, when several beans answer to one type:

| Situation | Outcome |
|---|---|
| One bean | It wins |
| A user bean and a `#[default_impl]` | The user bean |
| Several beans, exactly one `#[primary]` | The primary one |
| Several beans, zero or ≥2 `#[primary]` | `DiError::Ambiguous` |
| Asked via `get_qualified` | The matching `#[qualifier]` |

Two primaries are as ambiguous as none. Reporting is the point; picking the first
would be the bug this design exists to avoid.

**Hard and soft dependencies are ordered differently.** `refresh` runs Kahn's
algorithm, but a hard dependency (`Arc<T>`) needs *one* provider built before its
dependent, while a soft one (`Option<Arc<T>>`, `Vec<Arc<T>>`) waits for *all*
batch providers — so a `Vec<Arc<dyn Handler>>` observes the complete set rather
than whichever handlers happened to be built first.

A cycle among hard dependencies is `DiError::CircularDependency`. A stall on soft
dependencies only is *not* an error: mutually-optional beans are built anyway and
the optionals resolve to `None`.

**What the macro emits** is a `Buildable` impl (resolve each `#[inject]` field) and
a `RegistersComponent` impl (declare `dependencies`, `provides`, origin, primary,
qualifier). Because `build` reads its dependencies through the `Container` trait
rather than a concrete `AppContext`, a test can supply a mock container and
construct a component against fakes.

## Drawbacks

**Silent override is a knife with two edges.** The ergonomics are excellent — you
override by writing a bean — but nothing tells you that you have shadowed a
framework default. Define a bean whose type collides with one you did not know
existed, and the framework's behaviour changes with no diagnostic. Spring's
`@ConditionalOnMissingBean` is at least visible at the definition site.
`ARCHITECTURE.md` proposes a debug-build warning; it is not implemented.

**The error messages are worse than they look here.** `DiError::CircularDependency`
reports the set of components still blocked, not the edge that closed the cycle.
For four beans in a ring, the user gets four names and no arrow. Spring reports an
ordered path.

**Compile time and generated code.** Every component expands to two trait impls.
This is charged to every build, and it grows with the application.

**No runtime reconfiguration.** Wiring is fixed at compile time, so there is no
equivalent of swapping a bean via a config file, and no `@Profile` that selects an
implementation without a rebuild. For applications that genuinely deploy one
binary across environments with different wiring, this is a real loss.

## Rationale and alternatives

**A runtime registry with `inventory` or `linkme`.** Crates exist that collect
distributed static registrations at link time, which would allow a
Spring-shaped runtime scan. Rejected: it moves failures back to startup for no
gain in expressiveness, relies on linker behaviour that varies across platforms
and is fragile under `--gc-sections`, and does not work for a `cdylib` — which
[the hot-reload plan][hotreload] requires.

[hotreload]: ../internal/FULL_PLAN.md

**Explicit wiring, no macro.** Have the user construct the graph by hand in
`main`. Honest, debuggable, no magic — and it is what `AppContext::register_instance`
still supports. Rejected as the *default* because it scales badly: the ordering
burden lands on the user, and a 60-bean application becomes a 60-line topological
sort maintained by hand. The escape hatch remains for those who want it.

**Error on override instead of silent replacement.** Require an explicit opt-out,
Spring's `@ConditionalOnMissingBean` direction. Rejected for ergonomics — "override
by existing" is the property that makes the framework feel unopinionated, and it is
the thing users say they like about Spring. This is the closest call in this KEP,
and the Drawbacks section is where the cost is recorded. A debug-build warning is
the compromise that has not been built yet.

**Take the first bean on ambiguity.** Rejected outright. A framework that picks
arbitrarily produces a bug that reproduces only sometimes, and that is the worst
kind to own.

## Prior art

- **Spring Boot's auto-configuration** — `@ConditionalOnMissingBean` is exactly
  this feature, done at runtime and stated explicitly at the definition site.
  Kernway takes the behaviour and drops the annotation.
- **Dagger (Java/Android)** — compile-time DI via annotation processing, and the
  closest prior art for the *mechanism*. Demonstrates that generated wiring scales
  to large applications.
- **Spring's `@Primary` / `@Qualifier`** — adopted nearly unchanged, because the
  disambiguation vocabulary is genuinely good and users arriving from Spring
  already know it.
- **`shaku`, `teloc` (Rust)** — compile-time DI containers in Rust. Both require
  more explicit registration than Kernway; the auto-wiring-by-derive style is the
  main departure.

## Unresolved questions

- The override warning in debug builds is specified in `ARCHITECTURE.md` and not
  implemented. Should it be a warning, or should overriding require an opt-in
  attribute after all?
- Can `CircularDependency` report an actual path rather than a set? The
  information exists in the declared graph.
- Scopes. Every bean is effectively a singleton; there is no request scope or
  prototype scope. Whether those are needed, and what they would mean under
  thread-per-core ([KEP-0001](0001-thread-per-core-runtime.md)), is open.

## Future possibilities

- A `kernway beans` command that prints the resolved graph, including which
  defaults were overridden — which would address the silent-override drawback
  without changing the ergonomics.
- Compile-time detection of the ambiguity case, so `DiError::Ambiguous` becomes
  unreachable rather than merely rare.
- Request scope, if thread-per-core makes it cheap enough to be worth having.
